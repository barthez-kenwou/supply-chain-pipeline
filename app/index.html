Ce dépôt est un kit de delivery OCI : CI, contrôles de sécurité, image scannée et signée, déploiement par digest. La page est une vitrine légère ; la valeur est la chaîne — celle que j’exploite déjà en production sur zenora360.com.

/health · live Registry · Cosign · Compose fail-closed

En une phrase

J’ai extrait la chaîne DevSecOps que je fais tourner pour livrer un conteneur en production, et je l’ai publiée comme kit : copiez .github/ + deploy/, branchez vos secrets, livrez. L’app ici n’est qu’un nginx statique — le produit, c’est le chemin jusqu’à prod.

Ce que vous voyez tourner derrière cette page

  1. CI — Hadolint, Gitleaks, build image + probe /health, SonarQube si configuré
  2. Security — Trivy fs/config, CodeQL (Actions), ZAP baseline (cron / manuel)
  3. Release — build local → gate Trivy image → push Harbor → Cosign keyless → SBOM → provenance GitHub
  4. Deploy — cosign verify avant SSH → image par digest (ou artifact si Harbor 412) → health + rollback → smoke réseau proxy

La chaîne, étape par étape

Ci-dessous : ce qui part vraiment dans GitHub Actions — pas un schéma marketing. Chaque étape existe parce qu’elle ferme une classe de risque que j’ai déjà croisée.

CI · Quality

Qualité & hygiène du dépôt

Avant de parler « sécu image », je m’assure que le Dockerfile et les assets de démo sont sains. Sur ce kit static : Hadolint, présence de app/index.html / nginx.conf, build Docker local, probe HTTP /health. Sur une app Node (ZENORA) : lint, typecheck, tests, coverage, build.

  • hadolint
  • docker build
  • curl /health
  • SonarQube QG (optionnel, fail-closed si secrets présents)

Pourquoi : un Dockerfile pourri ou un healthcheck mort ne doit pas arriver jusqu’à la signature. Sonar Community sans sonar.branch.name — les flags PR/branch cassent l’édition gratuite.

CI · Secrets

Gitleaks — secrets dans le repo

Scan du tree avec Gitleaks en conteneur éphémère. Pas de token Harbor, pas de clé SSH qui se balade dans un commit « oublié ».

  • gitleaks/gitleaks

Pourquoi : la supply chain commence dans Git. Un secret commité reste un incident même si l’image est parfaite.

Security · SAST / SCA

Trivy filesystem + config, CodeQL

Trivy gate HIGH/CRITICAL sur le filesystem et la config IaC/Compose/Dockerfile (unfixed ignorés volontairement — je ne bloque pas sur ce que le vendor n’a pas encore patché). SARIF poussé vers l’onglet Security GitHub.

CodeQL security-extended : sur ce repo static il n’y a pas de JS applicatif — j’analyse le langage actions (workflows). Sur ZENORA : javascript-typescript.

  • aquasecurity/trivy
  • github/codeql-action

Pourquoi : SAST sur le code/workflows + SCA/config avant même de builder l’image runtime. CodeQL mal calibré (JS sur un repo sans JS) fait échouer le gate pour de mauvaises raisons — autant scanner ce qui existe.

Security · DAST

OWASP ZAP baseline

Baseline ZAP en cron hebdo + workflow_dispatch, mode -I (informational) pour ne pas casser le gate sur du bruit edge/Cloudflare. Rapport HTML/JSON en artifact.

  • zaproxy/zap-baseline
  • .github/zap-rules.tsv

Pourquoi : DAST sur une URL réelle complète la vue « code + image ». Je ne veux pas qu’un faux positif WAF fasse croire que la supply chain est rouge chaque lundi.

Release · Build

Build local, push : false

Buildx charge l’image en local (supply-chain-web:ci-candidate). Aucun push Harbor tant que le scan image n’est pas vert. C’est non négociable : le registry n’est pas une poubelle de candidats.

  • docker/build-push-action · load: true
Release · Image gate

Trivy image HIGH/CRITICAL

Scan vuln + secret + misconfig sur l’image candidate. Échec = pas de tag sha-* dans Harbor. SARIF image uploadé aussi.

  • trivy-action · scanners vuln,secret,misconfig

Pourquoi : scanner le Dockerfile ne suffit pas. La surface runtime (nginx alpine + packages) est ce que vous exposez vraiment.

Release · Registry

Push Harbor + digest immuable

Push sha-<7 chars> (+ latest sur main comme alias pratique, jamais utilisé pour le deploy). Digest résolu via RepoDigests locaux après push — pas de crane digest GET qui se fait jeter par une policy Cosign Harbor (HTTP 412).

  • Harbor OCI
  • docker push + retry
Release · Sign & SBOM

Cosign keyless, SBOM SPDX, provenance

Cosign keyless OIDC GitHub Actions (Fulcio / Rekor) — pas de clé privée à rotater dans les secrets pour la démo. Signatures sur REPO@DIGEST. SBOM SPDX via Anchore/Syft attaché à l’image. Provenance build : GitHub Attestations (push-to-registry: false — Harbor 412 sur upload OCI d’attestations).

  • sigstore/cosign keyless
  • anchore/sbom-action · SPDX
  • actions/attest-build-provenance

Pourquoi keyless : identité = workflow GitHub + OIDC. Auditable, pas de PEM Cosign qui fuit. Pourquoi SBOM : inventaire exploitable le jour du prochain CVE nginx/openssl.

Deploy

Verify → SSH mux → runtime → smoke

1) cosign verify sur le digest avant toute ouverture SSH.
2) Une session SSH ControlMaster (UFW limit + scp/ssh en rafale = timeouts — déjà vécu).
3) Image : pull @sha256, ou docker load de l’artifact release-image si Harbor Cosign policy bloque le pull (412).
4) Health /health, rollback avec preuve, smoke sur le réseau Docker du reverse proxy (pas seulement HTTPS public — Cloudflare peut 403).

  • Cosign verify
  • Docker Compose
  • Nginx Proxy Manager
  • known_hosts piné

Pourquoi j’ai choisi ça — et pas autre chose

Option B : site static nginx

Le portfolio doit montrer la chaîne, pas un second monolithe React à maintenir. Static HTML = surface d’attaque minimale, build trivial, même Dockerfile multi-stage discipline (user non-root, read-only, healthcheck). Vous remplacez app/ par votre vrai service ; vous gardez .github/ + deploy/.

Digest, jamais latest en prod

Un tag est mutable. Un digest est un pointeur de contenu. Deployer @sha256:…, c’est savoir exactement ce qui tourne — et pouvoir prouver que Cosign a signé ce bytes-là. sha-* reste un alias humain ; latest est refusé dans le workflow Deploy.

Cosign keyless (OIDC GitHub)

Pas de clé Cosign longue durée dans les secrets du repo démo. L’identité de signature = le workflow + le dépôt. Verify côté Deploy avec issuer token.actions.githubusercontent.com et regexp sur release.yml.

Trivy avant push, pas « on verra au runtime »

Si Harbor contient déjà l’image vulnérable, vous avez perdu. Gate image HIGH/CRITICAL fail-closed sur le candidat local. SARIF pour la piste d’audit dans GitHub Security.

SSH ControlMaster + known_hosts piné

UFW en mode limit + une rafale scp/ssh = i/o timeout fantôme. Une session muxée. StrictHostKeyChecking=yes + secret DEPLOY_SSH_KNOWN_HOSTS obligatoire — pas de TOFU en CI.

Actions pinées SHA

Les actions critiques sont pinées sur un commit SHA, pas sur un tag flottant @v4. Supply chain du CI elle-même.

Slack : bruit maîtrisé

Échecs Release seulement. Deploy : succès et échec. Un Release vert ne spam pas le canal — le badge Actions suffit.

Ce que je n’ai pas mis (volontairement)

  • Kubernetes pour une image nginx — complexité ops sans gain ici.
  • Policy Harbor « Cosign » activée avec signatures keyless GitHub — casse les pulls (412). Enforcement = verify dans Actions.
  • Microservices, service mesh, « enterprise » cosmétiques.

Retours terrain — ce qui a cassé, ce que j’ai fait

Une supply chain « powerpoint » ne montre jamais les 412 et les timeouts. Voici ce que ce kit a absorbé en conditions réelles.

Harbor HTTP 412 — Cosign project policy

Symptôme : docker pull …@sha256:… → Precondition Failed / PROJECTPOLICYVIOLATION: not signed by cosign, même après un cosign sign keyless réussi.

Cause : le toggle Harbor « Deployment security → Cosign » ne traite pas correctement les signatures Sigstore keyless GitHub comme « signed » pour autoriser le pull.

Remède kit : artifact release-image (docker save) → Deploy fait docker load après verify. Remède ops : désactiver le toggle ; l’enforcement reste cosign verify avant SSH.

CodeQL « no JavaScript/TypeScript »

Repo static : pas de sources JS. CodeQL en javascript-typescript finalisait en erreur fatale. Fix : langage actions — on scanne ce qui existe vraiment (les workflows).

crane digest vs RepoDigests

Après push, un GET manifesto non signé se fait jeter (412). Digest pris depuis docker image inspect … RepoDigests en local, puis sign.

SSH timeouts sous UFW limit

Plusieurs connexions scp/ssh rapprochées → timeout. Une seule session ControlMaster pour copy + remote-deploy + smoke.

Dependabot npm sans package.json

Écosystème npm sur un repo static = job en erreur permanent. Dependabot limité à docker + github-actions.

Smoke HTTPS public 403

Cloudflare Bot Fight peut 403 le runner. Smoke qui compte = conteneur + réseau proxy. /health public = best-effort + exception edge recommandée.

Intégrer la supply chain dans votre projet

Vous ne réécrivez pas la chaîne. Vous greffez la colonne vertébrale sur votre application (Node, Go, static, peu importe) et vous adaptez les noms, le registry et la cible d’exécution. Ce kit est un modèle de référence — Harbor + VPS + Nginx Proxy Manager sont un déploiement possible, pas une obligation.

Registry

Harbor, GHCR, ECR, GCR… le contrat reste le même : push d’une image adressable par digest, signature Cosign, verify avant deploy. Remplacez les secrets HARBOR_* et les scripts de login par l’équivalent de votre registry.

Cible d’exécution

VPS Docker, VM cloud, ECS, Cloud Run, Kubernetes… le Release produit toujours une image signée. Seul le job Deploy change : SSH + Compose, ou kubectl set image, ou un service cloud qui tire le digest.

Ingress / reverse proxy

Nginx Proxy Manager, Traefik, Caddy, ALB, Ingress NGINX : l’app n’écoute qu’en interne. Branchez l’upstream sur le nom DNS Docker (ou le Service) et le port interne — sans republier :80 sur l’hôte si le proxy le tient déjà.

Qualité & SAST

Sonar, CodeQL, coverage : activez ce qui correspond à votre stack. Secrets absents = skip explicite. Secrets présents = gate fail-closed. Alignez CodeQL sur le vrai langage du dépôt.

Étape 01

Récupérer le squelette

Depuis supply-chain-pipeline, copiez dans votre dépôt :

  • .github/workflows/ · .github/scripts/ · dependabot.yml · zap-rules.tsv
  • deploy/remote-deploy.sh · deploy/smoke-test.sh (si vous déployez par SSH)
  • docker-compose.yml si le modèle Compose vous convient

Ce que vous ne copiez pas forcément : le dossier app/ vitrine. Remplacez-le par votre Dockerfile / service. Conservez un endpoint /health (ou adaptez les scripts).

Étape 02

Renommer pour votre produit

Recherchez-remplacez ces identifiants :

  • IMAGE_NAME → ex. mon-api
  • supply-chain-web → nom du conteneur / service
  • sonar.projectKey
  • titres Slack / summaries
  • environment production (si vous en avez plusieurs)

Application Node : remplacez reusable-quality.yml par lint / test / build / coverage. Static ou binaire : conservez Hadolint + build image + health.

Étape 03

Brancher votre registry

Harbor (référence du kit) — secrets HARBOR_REGISTRY, HARBOR_PROJECT, HARBOR_USERNAME, HARBOR_PASSWORD. Host only, lowercase, sans https://. Cosign project policy OFF si vous signez en keyless GitHub (sinon pulls HTTP 412).

GHCR — authentifiez avec GITHUB_TOKEN / packages: write, poussez vers ghcr.io/<org>/<image>, signez le digest, vérifiez avant deploy. Adaptez les noms de secrets dans Release / Deploy.

ECR / autre cloud — login via OIDC ou clés IAM, même séquence : build → scan → push digest → Cosign → verify → rollout.

Le kit livre aussi un artifact release-image (docker save) pour les cas où le registry bloque le pull (ex. Harbor 412) : utile en VPS, souvent inutile sur un orchestrateur cloud qui tire directement le digest.

Étape 04

Choisir où tourne la prod

VPS + Compose (référence) — Docker, réseau partagé avec le reverse proxy (PROXY_NETWORK), upstream CONTENEUR:port, secrets SSH d’environment production.

Cloud managé — remplacez le job Deploy SSH par le rollout natif (ECS task definition, Cloud Run revision, Helm/Argo, etc.) en gardant cosign verify avant le basculement.

Kubernetes — image par digest dans le manifeste, admission éventuelle (Kyverno/Gatekeeper) + verify CI ; le smoke devient un probe cluster plutôt qu’un curl sur le réseau Docker d’un VPS.

Peu importe la cible : prod = digest, jamais latest ; verify avant exposition ; health / rollback avec preuve.

Étape 05

Secrets, protections, premier vert

  1. Environment GitHub production (branches main only) si vous déployez depuis Actions.
  2. Branch protection : checks CI summary + Security summary.
  3. Optionnel : Sonar (SONAR_*), Slack, ZAP schedule.
  4. Feature branch → CI ; merge main → Release → Deploy.

Étape 06

Checklist « c’est en prod »

  • Image registry taguée + digest signé Cosign
  • Runtime healthy (conteneur, tâche ou pods)
  • /health (ou probe équivalent) OK en interne
  • Rollback testé au moins une fois
  • Badges CI / Security / Release sur votre README
  • Personne ne déploie latest à la main
